## 二、AV1 剩余缺陷 A：5 帧 `refresh_frame_flags` 写错

失败帧固定 30/60/90/120/150，全部是"源 `0x10`、合成 `0x00`"。

根因是**结构性死锁**（已完整测绘，未解）：正确值必须用**下一帧**的
`ref_frame_map` 反算，而 ffmpeg 的短超时轮询会在下一帧到达前触发 flush，
被 flush 送出的帧再无机会改写。

- flush 命中 75 次（70 次 `bitpos=50`、5 次 `bitpos=58`）
- 失败的 5 帧正是 `bitpos=58` 那批
- 四种写法实测：写 0 → **140/150**（当时最好）；保留轮转占位 → 70/150；
  恒 `1<<(slot-1)` → 85/150；仅 `bitpos==58` 时用 `1<<(slot-1)` → 140/150 无变化
- `DMD_AV1_NO_FLUSH=1` → 合成 5/5 全对，但会话停摆（送 5 收 1）

**flush 是所有剩余合成缺陷的来源，却又不能移除。**

## 三、AV1 剩余缺陷 B：70 个 show_existing_frame 未复现

源码流结构（按 TEMPORAL_DELIMITER 切分，第 65 轮实测）：

```
150 个 TU：70 个只含一个 SEF（无帧数据）
           45 含 1 帧、15 含 2 帧、10 含 3 帧、5 含 4 帧、5 含 5 帧
合计 150 OBU_FRAME（其中 show_frame=1 仅 80 个）+ 70 个 SEF
80 真实显示 + 70 复显 = 150 = 软解输出帧数
```

硬件行为**完全正确**：送 150 收 80，与 `show_frame=1` 数量精确吻合。

单变量硬件级验证（`/tmp/sess3` 绕过驱动）：

```
源码流原样        送 150 收 150
剥掉全部 SEF 头   送 150 收  80   ← 与驱动合成流一致
```

`dmd_av1_build_show_existing()` 已实现，单测逐字节对齐源码流
（`map_idx=6 → [1a 01 e8]`、`5 → [1a 01 d8]`、`3 → [1a 01 b8]` 等 5 例全通过）。
但接入后破坏像素，故 **默认关闭**，`DMD_AV1_SEF=1` 显式开启调试。

### SEF 接入的四次失败（勿重复）

| 尝试 | 结果 |
|---|---|
| 在 EndPicture 路径追加 | 只补出 4 个（该路径 `show_frame=1` 仅 5 次经过） |
| 在 flush 路径追加 | 150 → 111 帧，耗时涨 4 倍 |
| 队列非空即送（不设门） | 150 → 64 帧 |
| 以"被引用 surface 已 READY"为门 | 同上；该条件几乎恒真，等价于无门 |

数量实验（`DMD_AV1_SEF_MAX=<n>`，不设门只限总数）：

```
8 → 150 ✓    20 → 150 ✓    40 → 超时    ~68 → 64 帧
```

崩溃阈值在 20~40 之间且**与门无关**，所以"SEF 抢在被引用帧解码前送出"
这个归因是错的（第 66 轮否证）。真正的自变量是 SEF 单元数量本身。

**已知副作用（第 68 轮发现，此前潜伏三轮）**：即使只补 4 个 SEF，
30 帧样本的不同画面数就从 17 腰斩到 8。成因：SEF 复显帧回来时驱动
没为它们登记 pending，ffmpeg 按自己的映射取像素，取到了错的 surface。

> ⚠️ 帧数（150）与合成正确率（145/150）对这个退化**完全不敏感**。
> 新增任何"会产生额外输出帧"的机制后，必须同时测像素的不同画面数。

## 四、配对编号：一个看似正确的改法已被否证

回传 `unit_seq` 来自 session 的 `units_sent`，而 pending 登记用
`++units_submitted`（按 EndPicture 计数）。实测登记 `6,7,9,10,13,14`
而回传 `1,2,3,4,6,7`，150 帧里回退 **79** 次 —— 编号确实不同源。

改用 `units_sent + 1` 后：回退 79→64、精确命中 21→26/30，看着在改善，
**但不同画面数从 17 掉到 4~5**。回退路径的顺序推断反而给出更合理的配对，
"精确匹配"匹配到了错的帧。说明编号不同源只是表象，真正的错位在别处。
两处（flush 与主路径）均已撤回。

## 六、方法教训（本会话代价最高的几条）

1. **日志行数 ≠ 执行次数。** 用 `grep -c` 数日志推断调用次数，两次得出错误
   结论（"220 次 EndPicture"、"75 次取槽"）。改用无条件计数器后矛盾自解。
2. **改完先确认改动生效，再解读结果。** `if (ft == 0 /* KEY_FRAME */) {`
   在 `decode.c` 里有两处完全相同的文本，第 63 轮的开关落在错的那处，
   我却把"统计毫无变化"当成"无法解释的矛盾"分析了一整轮。
3. **单一判据会骗人。** 帧数对像素退化不敏感；"精确命中数"上升的同时
   真实质量在崩。**不同画面数**才是 AV1 像素的有效判据。
4. **一个数据点永远能配出多种因果。** 把可疑变量拉成曲线（8/20/40/68）
   一测，"SEF 抢跑"假说自己就死了。
5. **先测源材料的真实结构，再设计机制。** SEF 独占 TU 这件事，一句
   `python3` 按 TD 切分就能看出来，我却基于错的结构折腾了三轮。
6. **边界丢弃必须留痕。** `if (count < 8)` 静默跳过丢了 58 次入队，
   毫无迹象，害我去猜时序问题。
7. **增量构建的零警告不可信。** 一处嵌套注释警告只在 `make clean` 时暴露。
8. **小样本"全对"不是修好。** 6 帧样本同时藏了三个缺陷（`allow_warped_motion`、
   `lr_type` 映射、`lr_unit_shift`），样本 6 → 24 → 60 → 150 放大才暴露。

## 排查工具

`vaapi-driver/tools/probe_av1_feed.c` —— 把 OBU temporal unit 直送
`/dev/video32`，绕过整个 VA-API 驱动。这是隔离"合成问题"与"硬件问题"的
关键手段：

```
cc -O2 -o probe_av1_feed vaapi-driver/tools/probe_av1_feed.c
./probe_av1_feed av1_1080p.obu
```

判据：

| 结果 | 结论 |
|---|---|
| 直送源码流能吐满帧 | 硬件没问题，缺陷在驱动的 OBU 合成侧 |
| 直送源码流也吐不满 | 硬件/内核侧的问题，与合成无关 |
| 始终无 `SOURCE_CHANGE` | 该设备解码会话起不来，先跑 `probe_device_support` |

正是这个手段在第 68 轮推翻了"SEF 复显由 ffmpeg 自行完成"的假设：
源码流直送收 150 帧，而驱动合成流只收 80 帧，两条流的 OBU 构成差异
只有那 70 个 `show_existing_frame` FRAME_HEADER。

> ⚠️ 探针必须用 burst 模式（一次灌完再统一收帧）。AV1 解码器有
> output delay，逐单元等帧会死锁 —— 它要收满 N 个输入才吐第一帧，
> 而调用方在等第一帧。这个坑在旧版探针上踩过。

> ⚠️ 旧版探针 `tools/av1_probe.py` 与 `tools/av1_probe_native.c` 走的是
> daemon 线协议，随 daemon 一起在 0.4.0 删除，已由上面这个 V4L2 版替代。

## 第 95 轮：上一轮的"色度缺尾 24 行"是测量错误，真缺陷是 SEF

### ⚠️ 先更正一个已推送的错误结论

提交 `4127030` 写道"亮度平面全量一致，色度平面最后 24 行硬解全为 0"，
并据此把嫌疑指向 `image.c` 的 `nv12_copy`。**那个结论是错的**，
根因是我按 **1920x1088** 切分帧，而落盘文件是 **1920x1080**：

```
按 1920x1088 切: 帧大小 3133440，466560000/3133440 = 148.897  ✗ 不整除
按 1920x1080 切: 帧大小 3110400，466560000/3110400 = 150.000  ✓ 整除
```

每帧偏移 23040 字节、逐帧累积错位，于是"最后 24 行为 0"和
"亮度完全一致"都是错位的产物。`nv12_copy` 没有问题。

教训：**切分二进制流之前先验证帧大小能整除文件大小。** 一次除法就能
挡住这个错误，我却基于它做了完整的色度平面分析并写进了提交信息。
（1088 是 `G_FMT(CAPTURE)` 的对齐高度，确有其事 —— 但 ffmpeg 落盘的是
裁剪后的可见尺寸 1080，两者不能混用。）

### 按正确尺寸重测的真实缺陷

| 指标 | 硬解 | 软解 |
|---|---|---|
| 帧数 | 150 | 150 |
| 不同画面数 | **81** | **150** |
| 逐帧不同 | 74 帧 | — |
| 首个不同帧 | 2 | — |

差异帧的分布是决定性线索：

```
偶数帧 75 个，其中 70 个与软解不同
奇数帧 75 个，其中  4 个与软解不同
```

**70 正是源码流里 show_existing_frame 的数量**（`trace_headers` 实测）。
偶数位就是 SEF 应当出现的位置。所以缺陷收敛为一句话：
**70 个 SEF 帧没有被复现，硬解在这些位置输出了别的内容。**

### SEF 机制的现状：默认完全关闭

入队条件带 `getenv("DMD_AV1_SEF")`，不设该变量则一个 SEF 都不入队。
这解释了一个本轮的观测矛盾：把送出门（`av1_send_show`）完全放开，
结果与关闭时**逐位相同**（81 画面 / 74 帧不同）—— 因为队列始终是空的，
门开不开都没有东西可送。

> ⚠️ 方法教训：改一个开关后结果**逐位不变**，第一反应应当是
> "这条路径根本没执行"，而不是"改动无效"。本轮先怀疑了后者。

### 启用 SEF 后反而更差（两次尝试都是负向）

| 配置 | 帧数 | 不同画面数 |
|---|---|---|
| SEF 未入队（默认） | 150 | 81 |
| SEF 入队 + 门全开 | 73 | 20 |
| 再把 SEF 移到主帧**之后**送 | 63 | 18 |

第二次尝试基于一个假设：SEF 引用的槽位来自 `dpb_next_slot`，
即本帧**即将写入**的槽，此刻尚未解码，所以复显的是旧内容 ——
那就把 SEF 挪到主帧之后送。结果 73 → 63，更差。

**假设被否证，顺序不是根因。** 已按"同一方向失败两次就停止微调"
回退全部改动（`decode.c` 恢复到本轮起点，临时开关 `DMD_AV1_SEFGATE`
已清除，构建与单测复核通过）。

### 下一步的正确方向

本轮最后一个观测指向了一个更根本的问题：

```
源码流 SEF 帧数              70
驱动收到的 picture 数       110
ffmpeg 输出帧数             150
```

`110 + 70 = 180 ≠ 150`，而 `150 - 110 = 40`。驱动只被交付 110 个
picture 却要产出 150 帧，说明 **ffmpeg 对 SEF 的处理方式与"每帧调用一次
驱动"的假设不符**。另一条支持证据：VA-API 的 `va_dec_av1.h` 里
**既没有 `show_existing_frame` 也没有 `frame_to_show_map_idx` 字段**，
驱动无从得知上层想复显哪一帧。

所以下一轮应先回答"这 110 与 150 的差额是怎么产生的"，
在此之前不要再调 SEF 的门、数量或顺序 —— 那是第 65~68 轮和本轮
反复走过的路，共失败四次。

> 顺带作废一条旧记录：第 68 轮记的"SEF 无上限 → 64 帧、上限 40 → 超时"
> 在本设备（内核 6.6）**不复现**：门全开跑出 150 帧、耗时 1 秒。
> 那条记录属于 nabu（内核 4.14），不是通用结论。
